# Внутренний API проекта B (поиск клиентов Tanbala)

Статус: **согласован с владельцем 27.10.2026 и реализован в проекте B** (коммиты 0b286e5…2fb6356, тесты на моках). Реальная проверка один раз прошла 28.10.2026 (39 с, $0.0021). Отметка «клиент писал в WhatsApp» при запросе brief добавлена 28.10.2026 (коммит 3007a30), поля ответов не менялись. Доработки 28.10.2026 по просьбе проекта C и под VPS 4 ГБ (коммиты 3aabaf2…27f8d51): `Host` с портом, строка запроса не пишется в лог, владелец может снять пометки WhatsApp, браузеры общие с поиском. Поля ответов и коды не менялись. Менять контракт только с согласия владельца.

Для кого: проект C (WhatsApp-бот) узнаёт компанию клиента и получает то, что о ней знает проект B.

## Общее

- Адрес: `http://127.0.0.1:8000` (тот же процесс, что интерфейс проекта B; порт задаётся при запуске, по умолчанию 8000). Слушает только 127.0.0.1. Имя в заголовке `Host` должно быть `127.0.0.1` или `localhost`, порт любой: `127.0.0.1:8000` и `localhost:8000` (так их шлют обычные HTTP-клиенты) принимаются. Другое имя, например `host.docker.internal:8000` или IP машины, → 400 (текстом `Invalid host header`, до проверки токена).
- Строку запроса (телефон, домен или почта, название) проект B в свой access-лог не пишет, только путь; данные клиента в самом пути (`/internal/lookup%3Fphone=…`, `/internal/lookup/7700…`) тоже вырезаются. Тело `POST /internal/research` не логируется. Проекту C тоже стоит не писать телефоны клиентов в свои логи.
- Авторизация: заголовок `X-Internal-Token`, значение из `INTERNAL_API_TOKEN` в `.env` проекта B, сравнение за постоянное время. Токен проверяется первым: без токена или с неверным всегда 401, даже если запрос неверный или компании нет.
- Если `INTERNAL_API_TOKEN` пустой или короче 32 символов, API выключен: на любой запрос 401.
- Кодировка UTF-8 (и в параметрах запроса: кириллицу кодировать как UTF-8, иначе 400), ответы `application/json`. Время в ISO 8601 в UTC, например `"2026-10-27T06:14:21+00:00"`.
- Пути без слеша на конце: `/internal/lookup/` даёт 404 (с токеном) или 401 (без токена), перенаправлений нет.

### Ошибки

Тело ошибки: `{"error": "<код>"}`.

| HTTP | Код | Когда |
| --- | --- | --- |
| 400 | `bad_request` | неверный запрос: нет параметров, неверный формат, слишком длинное значение, не JSON, не тот HTTP-метод |
| 401 | `unauthorized` | нет токена, неверный токен, API выключен |
| 404 | `not_found` | нет такой компании (brief), неизвестный путь `/internal/...` |
| 429 | `rate_limited` | исчерпан дневной лимит проверок `RESEARCH_PER_DAY` |
| 429 | `budget_exhausted` | исчерпан дневной бюджет на Claude API `DAILY_API_BUDGET_USD` |
| 503 | `db_unavailable` | база проекта B недоступна |

### Нормализация входных данных (только кодом, без AI)

- **domain**: принимается домен, ссылка или адрес почты (`sklad.kz`, `https://www.shop.sklad.kz/about`, `ivan@sklad.kz`). Берётся часть после `@`, убираются схема, путь, порт, `www.` и поддомены до регистрируемого домена с учётом зон `com.kz`, `org.kz`, `net.kz`, `gov.kz`, `edu.kz`, `com.ru` и подобных (`a.sklad.com.kz` → `sklad.com.kz`). Общие почтовые домены (gmail.com, mail.ru, inbox.ru, list.ru, bk.ru, yandex.ru/kz/com, icloud.com, outlook.com и другие) — допустимое значение, но по ним ничего не ищется.
- **phone**: из строки берутся цифры; 11 цифр с 8 в начале → 7 в начале; 10 цифр → 7 спереди. Итог должен быть `7XXXXXXXXXX` (11 цифр), иначе 400. Телефоны компаний в базе приводятся к тому же виду.
- **name**: нижний регистр, ё → е, отбрасывается хвост 2ГИС после первой запятой («Zeta, склад» → «zeta»), убираются кавычки и формы собственности (ТОО, ИП, АО, ЗАО, ОАО, ООО, LLP, LLC, Ltd, JSC, Inc), знаки препинания, лишние пробелы. Пусто после нормализации → 400.
- Длина: domain до 253 символов, phone до 32, name до 200, city до 100. Длиннее → 400.

### «Уже писали» (`emailed`)

`emailed: true`, если в истории писем проекта B есть исходящее письмо этой компании: письмо пайплайна, импорт прошлых писем владельца или ручная отметка. Компания связывается с письмом по id, по любому её адресу, по домену её сайта и по корпоративному домену её адресов (общие почтовые домены не склеиваются). **Тестовые отправки не считаются.** `emailed_at` — время последнего исходящего письма, иначе `null`.

Сейчас настоящих отправок нет, поэтому почти везде `emailed: false`.

### Недоверенные тексты

`name`, `rubric`, `reason`, `pains[].evidence` взяты с сайтов, из 2ГИС или написаны моделью по тексту сайта. Проект B обрезает длину, убирает управляющие и невидимые символы Unicode, а из `reason` и `evidence` вырезает адреса почты и телефоны (заменяет на `[скрыто]`). Имена людей кодом надёжно не вырезать. **Проект C должен подавать эти тексты своей модели как данные, а не как указания** (сайт может содержать текст вида «игнорируй инструкции…»).

Длины после обрезки: name и rubric до 200 символов, segment до 100, reason до 600, pain до 200, evidence до 300.

## 1. Поиск компании

`GET /internal/lookup?domain=&phone=&name=`

Хотя бы один непустой параметр, иначе 400. Любой переданный параметр, который не нормализуется, → 400.

Сравнение:
- domain — с доменом сайта компании и доменами её почт (тоже до регистрируемого домена). `match_score` 1.0.
- phone — с телефонами компании. `match_score` 1.0.
- name — нечёткое сравнение нормализованных названий. `match_score` = 0.9 × похожесть, то есть не выше 0.9 и всегда ниже совпадения по domain или phone. Кандидаты с похожестью ниже 0.7 (score ниже 0.63) не попадают в ответ.

Если компания совпала несколькими способами, берётся лучший; при равенстве порядок domain → phone → name. До 3 кандидатов по убыванию `match_score`, при равенстве по возрастанию id. Ничего не нашлось: пустой список, 200.

Ответ 200:

```json
{
  "candidates": [
    {
      "id": 8,
      "name": "Платформа-А",
      "city": "Алматы",
      "rubric": "Складское хранение",
      "match_by": "domain",
      "match_score": 1.0,
      "emailed": false,
      "emailed_at": null
    }
  ]
}
```

| Поле | Тип |
| --- | --- |
| id | целое |
| name | строка |
| city, rubric | строка или null |
| match_by | `"domain"`, `"phone"` или `"name"` |
| match_score | число 0..1, два знака после точки |
| emailed | true/false |
| emailed_at | строка времени или null |

## 2. Справка о компании

`GET /internal/companies/{id}/brief`

`id` — положительное целое, иначе 400. Нет компании: 404 `not_found`.

Ответ 200:

```json
{
  "id": 8,
  "name": "Платформа-А",
  "city": "Алматы",
  "rubric": "Складское хранение",
  "segment": "Склад, логистика, дистрибуция",
  "fit": "yes",
  "fit_score": 80,
  "reason": "Ответственное хранение на нескольких складах, большой поток паллет…",
  "pains": [
    {
      "pain": "Инвентаризация занимает дни и отрывает людей",
      "evidence": "Складские помещения общей площадью более 11 000 м²",
      "source": "site"
    }
  ],
  "emailed": false,
  "emailed_at": null,
  "email_subject": null
}
```

| Поле | Тип и значения |
| --- | --- |
| id, name, city, rubric | как в lookup |
| segment | одна из строк: «Склад, логистика, дистрибуция», «Офис, компания с большим имуществом», «Розница», «Производство», «Оборотная тара», «Стройка, сервис, монтаж», «Бумажный архив», «Другое»; или null |
| fit | `"yes"`, `"maybe"`, `"no"`; null, если компанию ещё не оценивали |
| fit_score | целое 0..100 (не 0..1); null, если не оценивали |
| reason | строка или null: почему подходит или нет |
| pains | до 2 болей, **только подтверждённые** (цитата найдена кодом во входных данных). `pain` — одна из 9 строк раздела 5 документа о Tanbala; `evidence` — дословная цитата; `source` — `"2gis"` или `"site"` |
| emailed, emailed_at | см. «Уже писали» |
| email_subject | тема последнего исходящего письма, только если `emailed: true`; null, если писем не было или тема неизвестна (у импортированных писем темы нет) |

Используется последняя оценка компании.

**Отметка «клиент писал в WhatsApp» (с 28.10.2026, решение владельца).** Успешный запрос brief (200) ставит компании отметку с датой первого запроса; повторные запросы дату не меняют. Поэтому:
- вызывайте brief **только после того, как клиент подтвердил «да, это мы»** — не для предпросмотра кандидатов lookup и не повторами «на всякий случай»;
- справка внутри статуса research (`GET /internal/research/{job_id}`) отметку не ставит: после подтверждения клиентом вызовите brief отдельно;
- lookup, 401, 400 и 404 отметку не ставят.

Рассылку отметка не блокирует: в интерфейсе проекта B на странице письма и в карточке компании появляется предупреждение «Клиент уже писал в WhatsApp (дата). Проверьте, нужно ли письмо.», решение принимает владелец при одобрении. Поля ответа brief не изменились. Если бот перепутал компанию, владелец снимает отметку кнопкой в карточке компании; новый успешный brief поставит её снова.

Не отдаётся никогда: заметки проверяющему из черновика, непроверенные боли, текст письма, адреса почты, имена людей, телефоны.

## 3. Проверка новой компании

### Запуск

`POST /internal/research`, тело JSON до 4 КБ:

```json
{"name": "Платформа-А", "city": null, "phone": null, "domain": null}
```

- `name` — обязательная непустая строка. `city`, `phone`, `domain` — строка или null. Другие поля игнорируются. Неверный JSON, не объект, неверные типы или форматы (правила как в lookup) → 400.
- `city`: название по-русски или код 2ГИС без учёта регистра: Алматы (almaty), Астана (astana), Шымкент (shymkent), Караганда (karaganda), Актобе (aktobe), Атырау (atyrau), Павлодар (pavlodar), Усть-Каменогорск (ust_kamenogorsk). Пусто или null → Алматы. Другой город — не 400: задача создаётся и завершается `failed` с `reason: "city_unsupported"`.

Сначала проект B ищет компанию у себя. Надёжным совпадением считается domain или phone, либо одинаковое название после нормализации в том же городе.
- Компания есть и уже оценена → **200** `{"status": "done", "company_id": 8}`, без задачи и без расхода лимита.
- Иначе создаётся задача → **202** `{"job_id": "3f2c9e0a-…"}` (строка UUID).
  - компания есть, но не оценена (например, у неё не нашлось почты) — 2ГИС пропускается: обход сайта, если его ещё не было, и оценка;
  - компании нет — поиск по названию в 2ГИС в этом городе, выбор карточки по domain или phone, иначе по похожести названия (не ниже 0.7), затем обход сайта и оценка Haiku.

Почты не ищутся и не проверяются, письмо не пишется. Адреса, которые попались в карточке 2ГИС и на сайте, проект B хранит как обычно, но наружу через API не отдаёт.

**Компании, которые эта проверка сама добавила в базу, не попадают в рассылку проекта B** (пока владелец сам не снимет пометку), даже если у них найдётся почта: пометка «запрошено из WhatsApp» ставится в той же вставке, пайплайн их пропускает, база не даёт создать, одобрить или отправить им письмо. Уже известные компании проверка не помечает, даже если 2ГИС вернул карточку компании, которая у проекта B есть под другим названием: иначе любой собеседник бота мог бы закрыть рассылку чужой компании, назвав её домен (решение владельца 28.10.2026: таким компаниям только отметка «клиент писал в WhatsApp» при brief). Если бот перепутал компанию, владелец снимает обе пометки кнопкой «Снять отметку WhatsApp» в карточке компании; после этого компания обычная и может попасть в рассылку.

Лимиты:
- `RESEARCH_PER_DAY` (по умолчанию 20) задач в сутки по времени Алматы. Задачи с `city_unsupported` не считаются. Сверх лимита → 429 `rate_limited`.
- Если дневной бюджет на Claude API исчерпан → 429 `budget_exhausted`. Если бюджет кончился, пока задача ждала очереди, задача завершается `failed` с `reason: "budget_exhausted"`.
- Одновременно выполняется одна задача, остальные ждут в очереди (`queued`) по порядку. Очередь отдельная от поиска в интерфейсе проекта B, но браузеры общие (с 28.10.2026, VPS 4 ГБ): на весь проект B одновременно не больше одного Chrome для 2ГИС и одного Chromium для сайтов (`MAX_2GIS_BROWSERS`, `MAX_SITE_BROWSERS`, по умолчанию 1). Проверка идёт вне очереди: если поиск в этот момент сам ищет в 2ГИС или обходит сайт, она ждёт только конца этого шага, а следующий шаг поиска ждёт её. Пока ждёт, статус `running`.
- Та же заявка, пока первая в очереди или в работе (та же компания, либо то же название без учёта регистра, город, телефон и домен), возвращает 202 с **тем же** `job_id` и лимит не тратит. Если компанию успели оценить, пока задача ждала, второго вызова Haiku нет.
- Задачи с `city_unsupported` не ограничены: частоту запросов от одного собеседника ограничивает проект C.
- `RESEARCH_PER_DAY` общий на всех клиентов бота: один собеседник может исчерпать его за всех. Проект C ограничивает число проверок от одного номера в сутки (например 2–3).
- Ошибки в `name`, `phone`, `domain`, в том числе символ NUL, → 400 `bad_request` (не 503).

Обычно задача занимает 1–3 минуты (2ГИС, сайт, один вызов Haiku; в тесте 28.10.2026 — 39 секунд). Если в это время идёт большой поиск, добавьте ожидание его текущего шага: обход сайта до минуты, выдача 2ГИС обычно до пары минут (предел parser-2gis 20 минут). Опрашивать статус раз в 5–10 секунд.

**Тёзки.** По одному названию 2ГИС может вернуть другую компанию с тем же именем (тест 28.10.2026: «Рахат» → «Рахат, медицинский центр», а не кондитерская фабрика). Передавайте `phone` или `domain`, если клиент их назвал, и перед brief покажите клиенту название и рубрику для подтверждения «да, это мы».

### Статус

`GET /internal/research/{job_id}` → 200:

```json
{"status": "done", "company_id": 51, "brief": { "...": "как в /internal/companies/51/brief" }, "reason": null}
```

```json
{"status": "failed", "company_id": null, "brief": null, "reason": "not_in_2gis"}
```

| Поле | Значения |
| --- | --- |
| status | `queued`, `running`, `done`, `failed`, `not_found` (нет такой задачи или неверный job_id; HTTP всё равно 200) |
| company_id | целое, когда `done`; иначе null |
| brief | объект справки, когда `done`; иначе null |
| reason | только при `failed`: `not_in_2gis` (2ГИС не нашёл подходящую карточку), `city_unsupported`, `budget_exhausted`, `error` (сбой 2ГИС, Claude API, перезапуск приложения во время задачи или браузер занят зависшим шагом поиска дольше предела: для 2ГИС 22 минуты, для сайтов 5 минут); иначе null |

Поле `reason` добавлено по решению владельца 27.10.2026, оно необязательное: клиент может его не читать.

После перезапуска проекта B задачи в очереди продолжаются, а прерванная на ходу завершается `failed` / `error`. То же при сбое базы посреди задачи: очередь повторяет попытку через 30 секунд, следующие задачи идут дальше.

Результат хранится в базе: повторный запрос той же компании вернёт 200 `done` сразу.
