# C-WhatsApp: передача для слияния с проектом B

Обновлено: 28.10.2026. Проект: `venmart-rfid/C-WhatsApp` (WhatsApp-бот Tanbala: Node.js 22, TypeScript, Baileys, Claude).
С проектом B вживую ничего не связано: всё сделано и проверено на моках строго по `contract/INTERNAL_API.md`.

## Что сделано

Бот определяет компанию клиента, получает от проекта B справку и продаёт через боли. Чат уходит менеджеру, когда
клиент согласен с пользой и спрашивает цену.

1. **Определение компании** по очереди, сначала бесплатно:
   - а) домен из бизнес-профиля WhatsApp (соцсети, площадки и общие почты отбрасываются) => `lookup?domain=`;
   - б) номер `7XXXXXXXXXX` => `lookup?phone=`;
   - в) подтверждённое имя бизнес-аккаунта или имя профиля с признаком компании => `lookup?name=`;
   - г) название из слов клиента (извлекается в существующей оценке интереса на Haiku) => `lookup?name=`;
   - д) только у бизнес-аккаунта и только если остальное ничего не дало: логотип с фото профиля (Haiku с картинкой,
     один раз на чат);
   - е) ничего не нашлось: бот один раз спрашивает, из какой компании клиент.

   Кандидат берётся, если совпадение по названию не ниже 0.8 и второй кандидат не ближе 0.1.
2. **Подтверждение.**
   - Бот один раз спрашивает «Вы из компании X, правильно?»; если клиент назвал компанию сам, спрашивает с городом.
   - Справка идёт в промпт только после «да». «Нет»: кандидат сброшен и больше не предлагается.
   - Кандидат и подтверждённая компания видны в панели.
3. **Проверка новой компании** (`POST /internal/research`):
   - не больше раза на чат и не больше 10 запусков за 24 часа на весь бот;
   - статус опрашивается не чаще раза в 5 с, задача ждётся не дольше 15 минут;
   - 429 или failed: бот работает без справки.
4. **Справка в промпте** отдельным блоком как данные: только рубрика и боли, причём только боли из раздела 5 документа
   о Tanbala. Без evidence, source и цифр о клиенте.
5. **«Мы писали вам на почту»** только при `emailed: true`.
6. **Продажа.**
   - Боли подаются как то, что бывает у похожих компаний, с вопросом.
   - Принцип работы, подтверждённый владельцем, объясняется любому клиенту. Решение под объект бот не предлагает.
   - Бот не ссылается на сайт и 2ГИС.
7. **Передача.**
   - Первый вопрос цены без рассказа о задаче чат не передаёт.
   - После согласия с болью или рассказа о задаче, а также при втором вопросе цены: hot и фраза «Цена сильно зависит
     от объёма. Передал ваш вопрос специалисту, он вам напишет.»
   - В уведомлении менеджеру: компания (или «не определена»), ссылка `{EMAIL_UI_URL}/companies/{id}`, подтверждённые
     клиентом боли.
8. **API недоступен.**
   - Таймаут 3 с, после сбоя пауза 60 с без запросов.
   - Бот работает без данных о компании, клиенту ничего не пишет, в лог только коды.
9. **Тесты.** 11 сценариев владельца на моках (сборка как в боте, поддельные только сеть, WhatsApp и модель), всего
   4508 тестов, покрытие около 99,7 процента.

Проверено ревью безопасности, ревью кода и ревью соответствия заданию (агенты Opus), затем повторным ревью
исправлений. Найденное исправлено в два круга (коммиты `1c170a6`, `63093c0`, `f8ab393`, `3b70cf0`); повторное ревью

## Как запустить локально

```powershell
cd C:\Users\bogda\Desktop\venmart-rfid\C-WhatsApp
npm ci                 # install-скрипты отключены, better-sqlite3 приезжает готовым бинарником
npm run check          # типы, линтер, тесты с порогом покрытия
npm run build
npm start              # бот; к WhatsApp подключается только при WA_ENABLED=true и привязанной сессии
```

- Панель: `http://127.0.0.1:3100`, пароль `ADMIN_PASSWORD`. Карточка чата показывает раздел «Компания».
- Определение компании включается непустым `INTERNAL_API_TOKEN` (32..512 видимых символов, тот же, что у проекта B).
  Без токена бот работает как раньше.
- Проба бизнес-профиля (только по разрешению владельца): остановить бота, `npm run build`,
  `npm run probe:business -- <номер>`, сразу после неё снова запустить бота.

## Переменные .env (только названия)

- Новые:
  - `EMAIL_API_URL`: по умолчанию `http://127.0.0.1:8000`, допускается только хост 127.0.0.1.
  - `INTERNAL_API_TOKEN`: секрет. При заданном токене запуск запрещён, если включён прокси Node для fetch
    (`NODE_USE_ENV_PROXY`, `--use-env-proxy`).
  - `EMAIL_UI_URL`: http только для 127.0.0.1 и localhost, иначе https.
- Прежние: `VENMART_ANTHROPIC_KEY`, `OPENROUTER_API_KEY`, `MANAGER_WHATSAPP`, `ADMIN_PASSWORD`, `WA_ENABLED`,
  `TEST_MODE`, `TEST_ALLOWLIST`, `WHATSAPP_SESSION_DIR`, `DATABASE_PATH`, `TOKEN_LOG_PATH`, `API_DAILY_LIMIT`,
  `API_DAILY_LIMIT_PER_CHAT`, `BACKLOG_MAX_AGE_HOURS`, `PANEL_HOST`, `PANEL_PORT`, `PANEL_ALLOWED_HOSTS`.
- Модели в `config/models.json`: ответ на Sonnet 5.5; проверка, оценка интереса и logo на Haiku 5.5.

## Что C отправляет в API проекта B

- **Заголовки:** `X-Internal-Token`, `Accept: application/json`; у POST `Content-Type: application/json`.
- **lookup:** ровно один параметр за запрос: domain (домен из бизнес-профиля), phone (11 цифр с 7), name (до 200 символов).
- **research:** `{name, city, phone, domain}`:
  - city со слов клиента как есть;
  - phone только у бизнес-аккаунта, иначе null;
  - domain из бизнес-профиля или null.
- **Повторы:**
  - временные сбои (сеть, 503, 401, 404, ответ не по контракту) повторяются на следующих сообщениях клиента;
  - POST research после таймаута не повторяется: запрос мог дойти.
- **Ответы:** проверяются по контракту (zod), строки чистятся и обрезаются. id справки сверяется с запрошенным.

## Вопросы к проекту B и к слиянию

1. **Host: решено.** Агент B ответил (28.10): сервер принимает `127.0.0.1:8000` и `localhost:8000`. C заголовок Host
   не задаёт, его ставит fetch из `EMAIL_API_URL`; при адресе по умолчанию уходит `Host: 127.0.0.1:8000`. Если 400
   повторится, C покажет заголовки запроса.
2. **Номер в access-логе.** Номер клиента, домен и название уходят в строке запроса GET `lookup` и могут попасть в
   access-лог B (uvicorn и подобные пишут путь с query). Нужно отключить или маскировать access-лог для
   `/internal/*` либо согласовать lookup через POST. Передано агенту B, он чинит.
3. **Пометка «запрошено из WhatsApp».** Она ставится и существующей компании, если на неё вышла проверка. Проверку
   запускают слова клиента, а их можно подделать: с разных номеров называть чужие компании и выбивать их из
   рассылки. C ограничивает это пределом 10 запусков в сутки и одним на чат. Стоит решить, не ставить ли пометку
   существующей компании только после подтверждения клиентом. Передано агенту B, он чинит.

   **Ответ C на вопрос B (28.10): проверка новой компании запускается не больше раза на чат.** После первого
   `POST /internal/research`, который мог дойти до B (202 queued, таймаут, ответ не по контракту, любой отказ B, в
   том числе 429 и 400), чат больше research не шлёт. Повтор только если запрос точно не дошёл до проверки (сеть,
   5xx, 401, 404) или B ответил «компания уже есть», а справку получить не удалось (тогда повтор до 3 раз, новой
   проверки в B он не запускает). Сверху общий предел C: 10 запусков за 24 часа на весь бот. Код:
   `src/company/research.ts` (`startResearch`, `RETRY_LATER`), `src/company/identify.ts`.
4. **Проверка id в статусе research.** В статусе `done` C не сверяет `brief.id` с `company_id`; B должен отдавать
   согласованные значения.
5. **Боли.** C передаёт модели только боли, текст которых есть в разделе 5 `knowledge/tanbala-agent.md` (сейчас 9
   строк). Если документ меняется, его нужно обновить в обоих проектах одновременно.

## Проверка getBusinessProfile

**Проведена 28.10.2026** по разрешению владельца, один запуск, на бизнес-аккаунте. QR не понадобился, код выхода 0,
лог пустой, сообщений за время пробы не пришло. Код: `src/probe-cli.ts`, `src/whatsapp/probe*.ts`.

| Поле профиля | По номеру | По @lid |
|---|---|---|
| бизнес-аккаунт | да | да |
| сайт (website) | нет, 0 адресов | нет, 0 адресов |
| почта | нет | нет |
| категория | да | да |
| описание | да | да |
| адрес | да | да |

Вывод: getBusinessProfile работает без QR и по номеру, и по @lid. У этого аккаунта сайта нет, поэтому шаг а
(домен из профиля) сработает только у тех клиентов, кто заполнил сайт; дальше идут шаги б, в, г, д и е.

**Что делает проба:**
- берёт тот же замок, что бот, и отказывается при запущенном боте, при `WA_ENABLED=false` и без привязанной сессии;
- QR не показывает никогда;
- делает один запрос по номеру и, если WhatsApp знает LID, один по LID;
- печатает JSON только с признаками полей (есть сайт, почта, категория и т.п.), без номера и значений.

**Известный риск:** проба подключается тем же устройством, что бот, и Baileys сам подтверждает накопленную
офлайн-очередь. Бот этих сообщений уже не получит, в телефоне они есть. Проба записывает такие чаты в `known_chats`
(правило этапа 8) и сообщает их число; если записала не все, ставит в базе флаг «список чатов неполный», и этап 8
не переключится, пока флаг стоит (снятие флага понадобится сделать на этапе 8). Запускать в тихое время, сразу после
остановки бота.

## Что не готово и известные проблемы

- **Живой прогон новых промптов 28.10** (WhatsApp владельца, `INTERNAL_API_TOKEN` пустой, то есть без данных о
  компании):
  - приветствие: ответ с одним вопросом, проверка Haiku пройдена с первого раза;
  - случай с 1С (голосовое: склад 5 000 м², ввоз и вывоз, 1С, цена): передача hot, текст «Да, мы проводим интеграцию
    с вашей 1С, детали зависят от вашей конфигурации. Цена сильно зависит от объёма. Передал ваш вопрос специалисту,
    он вам напишет.», проверка пройдена с первого раза (26.10 она дважды отклоняла такой текст);
  - правила цены скриптом на чистой истории тем же кодом конвейера: первый вопрос цены без задачи оставляет чат у
    бота («Цена сильно зависит от объёма и от задачи. Подскажите, что вы хотите учитывать?»), второй вопрос даёт hot
    с точной фразой владельца; обе проверки пройдены с первого раза.
- **Не проверено вживую:**
  - объяснение принципа работы (метки, ридеры на входах и выходах): сообщение владелец ещё не отправил;
  - диалог о компании с настоящим API B (токен пустой, B чинится). Проверить при слиянии: включить токен, написать с
    номера из `TEST_ALLOWLIST`, посмотреть раздел «Компания» в панели.
- **Закрытый режим:**
  - чат, который пишет только с адреса @lid (номер скрыт), до выключения `TEST_MODE` целиком отсекается, поэтому шаг
    с доменом из бизнес-профиля для скрытых номеров заработает только после этапа 8;
  - шлюз WhatsApp сам не запрашивает профиль и фото для чатов вне `TEST_ALLOWLIST`.
- **Задержка первого ответа.** На первом сообщении чата ответ ждёт бизнес-профиль WhatsApp (до 5 с) и бесплатные
  запросы к B (до 3 с каждый).
- **Ожидание очереди чата.** Поиск по названию, проверка новой компании и логотип идут после ответа, следующая пачка
  того же чата их ждёт.
- **Учёт вопроса о компании.** Вопрос «Вы из компании X?» считается заданным по флагу модели или по названию
  кандидата в отправленном тексте; ответа ждём, только если название стоит в вопросе. Ожидание снимается следующим
  ответом, передачей менеджеру и возвратом чата боту.
