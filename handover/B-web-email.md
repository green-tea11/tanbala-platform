# Handover: проект B (B-web-email) для слияния с WhatsApp-ботом

Обновлено: 28.10.2026. Для кого: агент, который сводит проекты B и C на одном VPS, и агент проекта C.

Проект B ищет компании Казахстана в 2ГИС, обходит их сайты, оценивает Claude Haiku (подходит ли RFID-учёт Tanbala, какие боли) и пишет черновики писем; письмо уходит только после одобрения человеком (сейчас отправка только тестовая, на адрес владельца). Внутренний handover проекта со всеми решениями: `B-web-email\HANDOVER.md`.

## Что сделано для проекта C

Внутренний API по контракту `D-Email+WhatsApp\contract\INTERNAL_API.md`, внутри того же FastAPI, что интерфейс проекта B:

- `GET /internal/lookup` — узнать компанию по домену, телефону, названию;
- `GET /internal/companies/{id}/brief` — что мы знаем о компании (оценка, причина, подтверждённые боли, писали ли); запрос ставит отметку «клиент писал в WhatsApp», поэтому вызывать после «да, это мы»;
- `POST /internal/research` + `GET /internal/research/{job_id}` — проверить новую компанию: 2ГИС → сайт → оценка Haiku, без поиска почт и писем.

Компании, которые проверка из WhatsApp сама добавила в базу, помечаются `companies.requested_via = 'whatsapp'` и **не попадают в рассылку** (решение владельца): пайплайн их пропускает, триггеры базы не дают создать, одобрить или отправить им письмо. Уже известные компании не помечаются, чтобы собеседник бота не мог закрыть рассылку чужой компании (решение владельца 28.10.2026): им только отметка «клиент писал в WhatsApp» при brief. Обе пометки владелец снимает кнопкой «Снять отметку WhatsApp» в карточке компании, если бот перепутал компанию.

Доработки 28.10.2026: `Host` с портом (`127.0.0.1:8000`, `localhost:8000`) проходит (так было и раньше, агента C сбила формулировка контракта; теперь закреплено тестами); строка запроса не пишется в access-лог (ни у одного пути); общий лимит браузеров для поиска и проверок из WhatsApp (см. «Память»).

## Как запустить локально (Windows, машина разработки)

```bash
docker compose up -d                                  # Postgres 17 (127.0.0.1:5432) и Reacher 0.11.10 (127.0.0.1:8080)
PYTHONUTF8=1 .venv/Scripts/python -m tanbala_leads web   # интерфейс и API: http://127.0.0.1:8000
PYTHONUTF8=1 .venv/Scripts/python -m pytest -q        # бесплатные тесты, нужен Docker
```

При старте `web` сам применяет миграции, помечает прерванные запуски и проверки, продолжает очередь проверок. Окружения: `.venv` (проект, crawl4ai, FastAPI) и `.venv-2gis` (parser-2gis, ему нужен pydantic<2, вызывается как CLI). Установка: `B-web-email\docs\SETUP.md`.

Проверка API с токеном (значение в `.env` проекта B):

```bash
curl -H "X-Internal-Token: $TOKEN" "http://127.0.0.1:8000/internal/lookup?domain=pel.kz"
```

## Что нужно на VPS

- **Python 3.11**, два окружения (`.venv` ≈ 0.8 ГБ, `.venv-2gis` ≈ 40 МБ).
- **Два браузера.** Google Chrome для parser-2gis: parser-2gis запускает его с окном, поэтому на сервере без экрана нужен **Xvfb**, либо проверить его флаг headless на 2ГИС. Chromium для crawl4ai (Playwright, ≈ 0.7 ГБ в `.browsers`) работает без окна, Xvfb ему не нужен. У каждого запуска parser-2gis свой профиль и свободный порт, параллельные запуски не мешают.
- **Postgres 17** (Docker, только 127.0.0.1). База сейчас 43 МБ. Docker-образы: postgres:17-alpine ≈ 0.4 ГБ, reacherhq/backend:v0.11.10 ≈ 1.4 ГБ.
- **Reacher** (проверка почт): исходящий **порт 25** (многие хостинги закрывают его по умолчанию, проверка: `scripts/check_port25.py`), **PTR-запись** IP и свой домен для `REACHER_HELLO_NAME` / `REACHER_FROM_EMAIL`, иначе почтовые серверы отвечают «неизвестно» или блокируют IP.
- **Память (замер 28.10.2026, Windows, поиск на 1 компанию и проверка из WhatsApp одновременно):** сервер Python 159 МБ в простое, до 257 МБ в работе; Chrome parser-2gis ≈ 1.0 ГБ на запуск (рабочий набор; частная ≈ 0.55 ГБ), два сразу 1.96 ГБ; Chromium crawl4ai ≈ 0.6 ГБ + драйвер Playwright ≈ 0.15 ГБ; пик всего сервера 2.23 ГБ, когда оба Chrome грузили 2ГИС. Postgres ≈ 0.22 ГБ, Reacher ≈ 8 МБ. Chrome тяжёлый, потому что parser-2gis запускает его с окном и грузит карту; без окна должен быть легче, на VPS проверить.
- **Лимит браузеров (с 28.10.2026, VPS 4 ГБ, решение владельца).** На весь сервер одновременно не больше одного Chrome для 2ГИС и одного Chromium для сайтов (`MAX_2GIS_BROWSERS`, `MAX_SITE_BROWSERS`). Проверка из WhatsApp идёт вне очереди между шагами большого поиска: ждёт его текущую выдачу 2ГИС или текущий сайт, а следующий шаг поиска ждёт её. Код: `tanbala_leads/browsers.py`. Лимит действует внутри процесса `web`; поиск из командной строки (`python -m tanbala_leads search`) — другой процесс, на VPS запускать поиск только из интерфейса (CLI `search` к тому же помечает идущий в сервере запуск прерванным). Сервер `web` запускать под systemd: parser-2gis на Linux работает в своей группе процессов, и при остановке сервера его Chrome убивает systemd (`KillMode=control-group`, по умолчанию), а не Ctrl+C.
- **Расчётный пик с лимитом** (по замеру выше, рабочий набор): сервер B ≈ 0.26 + Chrome 1.0 + Chromium 0.6 + драйвер 0.15 ≈ **2.0 ГБ** (было до 3.7 ГБ в худшем случае); вместе с Postgres ≈ 0.22, Reacher, WhatsApp-ботом ≈ 0.3 — **≈ 2.55 ГБ**, плюс система и Docker ≈ 0.4–0.5 ГБ — **≈ 3.0 ГБ из 4 ГБ**. Запас около 1 ГБ; на VPS включить swap 1–2 ГБ на случай всплеска и проверить замер на Linux (Chrome под Xvfb или без окна).
- **Диск:** код, окружения и браузеры ≈ 1.6 ГБ, образы ≈ 1.8 ГБ, плюс база и логи; 10 ГБ с запасом.
- **Сеть между проектами:** API слушает только 127.0.0.1 и проверяет имя в заголовке `Host` (127.0.0.1 или localhost, порт любой). Если бот C работает в Docker, 127.0.0.1 внутри контейнера — это сам контейнер: нужна сеть хоста (`network_mode: host`) или иной способ, который сохранит `Host: 127.0.0.1`. Решить при слиянии.
- Интерфейс проекта B без логина: на VPS держать его на 127.0.0.1 и открывать через SSH-туннель. Любой процесс на самом VPS (в том числе бот C) технически может открыть интерфейс и нажимать его кнопки; бот должен ходить только в `/internal/...`.
- Логи проекта B идут в stdout/stderr процесса `web` (на VPS — journald): access-лог без строки запроса, логи приложения от INFO (например, снятие отметки WhatsApp).

## Что не готово и известные проблемы

- Реальная проверка из WhatsApp сделана один раз (28.10.2026): «Рахат» → 39 с, $0.0021, но 2ГИС первым дал «Рахат, медицинский центр», а не фабрику. По одному названию бот может попасть в тёзку: передавать телефон или домен и подтверждать у клиента название и рубрику.
- Ложную отметку «клиент писал в WhatsApp» (собеседник бота назвал чужую компанию и ответил «да») владелец снимает вручную кнопкой в карточке; сама она не пропадает. Рассылку она не блокирует.
- Боевой отправки писем нет: только тест на адрес владельца. Тестовое письмо не дошло до Gmail: у почтового сервера venmart.kz (194.32.140.134) нет PTR-записи, нужно обращение к хостингу.
- В запуске №3 владельца (27.10.2026) Reacher не ответил для 12 компаний (`ReacherUnavailable`), причину ещё не разбирали.
- Reacher с домашнего IP даёт «неизвестно»: полная проверка почт только на VPS с PTR и своим доменом.
- Тексты справки взяты с сайтов и от модели: проект B чистит их (длина, невидимые символы, почты и телефоны), но **проект C должен подавать их своей модели как данные, а не как указания**.
- parser-2gis зависит от вёрстки 2ГИС и может сломаться при её изменении.
- Поиск по названию сравнивает со всеми компаниями в Python: на сотнях и тысячах компаний это быстро, на десятках тысяч понадобится `pg_trgm`. Частоту запросов от одного собеседника ограничивает проект C.
- Перед боевой отправкой писем (её пока нет) проверять `requested_via` в той же транзакции, что и отправку.
