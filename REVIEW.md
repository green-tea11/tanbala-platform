# Tanbala: вводная для внешнего ревью

Состояние на 04.11.2026, ветка `main`. Файл написан для ИИ-агента опытного разработчика, который видит проект впервые.
Он заменяет чтение всех документов: после него можно сразу идти в код. Если файл и код расходятся, прав код.

Владелец проекта не программист: бизнес знает, детали кода нет. Проект написан почти целиком агентами Claude Code
за две недели, поэтому внешний взгляд ему особенно нужен.

## 1. Задача ревью

Владелец просит независимую оценку: как работает портал (единая панель `panel.tanbala.kz` и две системы за ней),
крепка ли архитектура и что нужно исправить до запуска на настоящих клиентах.

Порядок работы:

1. Прочитать этот файл.
2. Запустить проверки на клоне (раздел 10).
3. Пройти вопросы раздела 13 по коду.
4. Отдать результат в формате раздела 14.

Рамки:

- Работа только с клоном. Доступа к серверу здесь нет и для ревью он не нужен.
- Не вызывать платные API (Claude, OpenRouter), не запускать поиск 2ГИС, не отправлять письма.
- Не подключать WhatsApp и не показывать QR. На номере Tanbala работает живая сессия, две копии одной сессии её
  ломают.
- Секретов в репозитории нет. Все тесты идут на моках, ключи для них не нужны.
- `main` не менять. Предложения идут в отчёт, код при необходимости в отдельную ветку.
- Файлы `CLAUDE.md` написаны для агента владельца. Запреты из них действуют, а порядок «отчёт и стоп до ок» к ревью
  не относится.

## 2. Что это за продукт

Tanbala, направление ТОО «VenMart» (Алматы), ставит учёт вещей на RFID-метках под ключ. Программа автоматизирует
привлечение клиентов:

1. **Почта** находит компании в 2ГИС, читает их сайты, оценивает моделью, проверяет адреса и готовит письмо. Письмо
   уходит только после одобрения человеком.
2. Клиент пишет в WhatsApp, из письма или с сайта. **Бот** консультирует его, выясняет задачу и определяет компанию.
3. Когда всё для расчёта известно, бот передаёт чат менеджеру: уведомление на номер менеджера и карточка в панели.
4. Менеджер отвечает из **панели** или с телефона и может вернуть чат боту с заметкой.

Пользователи панели: владелец (часто с телефона) и будущие менеджеры.

Система на настоящих клиентов ещё не запущена:

| Что | Состояние |
| --- | --- |
| Сервер | работает коммит `8793ee7`, службы `tanbala-leads`, `tanbala-whatsapp`, `tanbala-console` и Caddy активны |
| `main` | впереди сервера на 6 коммитов с правками бота (`412c2d7`…`f7c905d`), они не выложены |
| Бот | `TEST_MODE=true`: отвечает только номерам из списка |
| Письма | компаниям не уходят: боевая отправка в коде всегда отказывает, тест только на адрес владельца |
| Разбор ответов на письма | не сделан: `leads/tanbala_leads/steps/replies.py` бросает `NotImplementedError` |

## 4. Карта системы

```
клиент в WhatsApp ── Baileys, связанное устройство ──┐
                                                     ▼
браузер ─ https ─ Caddy ─ 127.0.0.1:3200 console ─┬─ X-Console-Token ─ 127.0.0.1:3101 whatsapp, API для консоли
         (пароль)         (BFF + SPA)             └─ X-Console-Token ─ 127.0.0.1:8000 leads, /internal/console/*

whatsapp ─ X-Internal-Token ─ 127.0.0.1:8000 leads, /internal/*  (поиск компании, справка, проверка новой компании)
leads ─ Postgres и Reacher в Docker на 127.0.0.1;  наружу: Claude API, 2ГИС, сайты компаний, SMTP
whatsapp ─ наружу: WhatsApp, Claude API, OpenRouter (расшифровка голосовых)
console ─ наружу никуда: только два внутренних API
```

| Часть | Папка | Стек | Данные | Порты | Код | Тесты |
| --- | --- | --- | --- | --- | --- | --- |
| Панель | `console/` | Node 22, TypeScript, fastify 5, React 19, Vite | SQLite: пользователи, сессии, журнал, отметки «видел» | 3200 | около 10 тыс. строк | 199 (сервер; у `web/` тестов нет) |
| Бот | `whatsapp/` | Node 22, TypeScript, Baileys 7.0.0-rc14, Anthropic SDK, fastify | SQLite (15 версий схемы), папка сессии, журнал токенов | 3100 старая панель, 3101 API | около 27 тыс. | 5985 |
| Почта | `leads/` | Python 3.11+, FastAPI, psycopg 3, Jinja, crawl4ai, parser-2gis | Postgres | 8000 API, 8001 старый интерфейс | около 9 тыс. | 2000 (362 нужен Postgres или платный вызов) |

Три части живут в одном репозитории, но это три отдельных процесса и три отдельных хранилища. Общего кода нет, связь
только по HTTP на `127.0.0.1`. Контракты: `contract/INTERNAL_API.md` (бот к почте), `contract/CONSOLE_API.md`
(панель к почте и боту), `console/docs/API.md` (браузер к панели).

## 6. Панель (console)

Главный предмет ревью. Это сервер-посредник (BFF) и одностраничный интерфейс. План и причины решений:
`console/docs/PLAN.md`. Что должно быть на экранах: `console/docs/PRODUCT.md`, опись 181 функции старых панелей:
`console/docs/FEATURES.md`.

**Сервер** (`console/src/`):

| Папка | Что |
| --- | --- |
| `config/` | разбор `.env`; панель не стартует при неверном токене, совпавших токенах или адресе не на 127.0.0.1 |
| `db/` | SQLite: пользователи (scrypt), сессии (хранится только SHA-256 id), журнал 180 дней, отметки «видел» |
| `auth/` | пароли, ограничитель входа, сессии |
| `backends/` | клиенты почты и бота: адрес из шаблона, таймаут, предел ответа, проверка схемой zod, кэш чтения 1.5 с, не больше 4 запросов сразу, предохранитель после 3 таймаутов на 10 с |
| `domain/` | расчёт расхода, склейка заметки, «писали после письма», полоса режима |
| `services/` | главная и карточки: собирает их из двух ответов сама |
| `server/` | fastify: хуки Host, HTTPS, Origin, сессия, роль, CSRF, заголовки; маршруты `routes/`, статика |

Браузер не видит токены почты и бота. Общего прокси нет: каждый маршрут `/api` объявлен отдельно с ролью
(`server/routes/define.ts`), тест падает, если у маршрута роль не указана. Если бот или почта не отвечают, их разделы
показывают «недоступно», остальное работает.

**Роли.** Владелец может всё. Менеджер смотрит, отвечает клиенту и возвращает чат боту, но не запускает поиск, не
трогает письма и не видит «Систему». Пользователей заводят только командой на сервере. В «Системе» владелец видит их список и входы и может закрыть сессии.

**Интерфейс** (`console/web/src/`): React без библиотек состояния, свой маленький роутер (`lib/router.tsx`), опрос
вместо WebSocket (`lib/usePoll.ts`): ход поиска раз в 2 с, рабочие экраны раз в 5 с, фон раз в 15 с, редкое раз в
60 с, только пока вкладка открыта. Экраны: вход, главная «Требует внимания», чаты, единая карточка клиента, компании,
письма, поиск, «Кому писали», уведомления, система. Рассчитан на 390 px так же, как на 1440 px.

Действие всегда идёт в те же функции, что кнопки старых панелей: `leads/tanbala_leads/web/actions.py` и
`whatsapp/src/panel/chat-actions.ts`.

## 7. Бот (whatsapp)

Один процесс: подключение к WhatsApp, конвейер ответа, старая панель (3100), API для консоли (3101). Внешние
библиотеки только в адаптерах (`src/whatsapp`, `src/llm`, `src/db`, `src/panel`), эту границу держит
`tests/guards/architecture.test.ts`. В `src/domain` только типы и порты, логика в `src/pipeline`, `src/agent`,
`src/checks`, `src/company`, `src/handoff`, `src/messaging`.

**Путь одного сообщения** (`src/pipeline/handle-inbound.ts`, `reply-flow.ts`, `decide.ts`):

1. Baileys отдаёт сообщение. Запись в базу, склейка пачки: тишина 4 с, не дольше 15 с (`batcher.ts`).
2. Чат ведёт менеджер: бот молчит. В `TEST_MODE` номера не из списка не обрабатываются вообще.
3. Голосовые расшифровываются через OpenRouter.
4. Бесплатные шаги определения компании: домен и номер из профиля, имя профиля, опрос идущей проверки, справка
   (`company/prepare.ts`).
5. Вызов `interest` (Sonnet) обновляет выжимку и уровень интереса, его итог по компании применяется до черновика.
6. Вызов `reply` (Sonnet) пишет черновик и выбирает исход: `answer`, `hot`, `no_answer`, `asked_human`, `complaint`.
7. Проверки кодом, бесплатные (`src/checks/`): тире, двоеточия, цены, стоп-слова, сроки, ссылки, жаргон, один голос,
   длина до 6 предложений и 550 знаков, повтор сильной стороны.
8. Вызов `review` (Sonnet) ищет только неправду, цену и обещание.
9. Не прошло: один повтор `reply` с замечаниями, `interest` заново не вызывается. Снова не прошло: у `answer` уходит
   безопасный вопрос (`safe-questions.ts`), а если спрашивать нечего, передача `check_failed`. У `hot`, `no_answer` и
   `asked_human` чат передаётся с той же причиной и фиксированной фразой. Сбой самого вызова Claude даёт `llm_error`.
10. Ответ уходит с паузой «печатает»: 200 мс на знак, от 1 до 20 с. Лимиты отправки: 30 в час на чат, 300 в час всего.
11. Только если ответ ушёл: поиск компании по словам клиента, проверка новой компании и логотип
    (`company/identify.ts`).

Обычно на сообщение 3 вызова Sonnet, при отказе проверки до 5. Если клиент написал во время ответа, пачка один раз
проходит заново, в худшем случае 10 вызовов. Один раз на чат бывает `logo` (Haiku), расшифровка голосового идёт в тот
же счётчик. Лимиты: 500 вызовов в сутки на бота и 100 на чат, при превышении бот замолкает и зовёт менеджера.

**Промпты** (`src/agent/prompts.ts`, `knowledge/bot.md`). 03.11.2026 ужаты по просьбе владельца: один файл знаний
вместо трёх, с 51 до 4.7 тысячи знаков. Постоянная часть вызова (знания, инструкция, правила указания коллеги,
описания полей) не больше 10 тысяч знаков, это проверяет тест; история и блок данных идут сверх этого. `interest`
знаний не получает. Слова клиента всегда идут как данные: угловые скобки заменяются, поэтому блоки `<данные>` и `<знания>`
подделать нельзя. Заметка менеджера идёт отдельным блоком в system.

**Передача.** Причины: `hot`, `no_answer`, `asked_human`, `complaint`, `check_failed`, `human_took_over`, `llm_error`,
`limit`. Код не верит модели на слово (`handoff-gate.ts`): `hot` принимается, только если есть причина: третий вопрос
цены, вопрос цены, сроков или договора при понятной задаче, два ухода от вопросов подряд, для расчёта известно всё. Без
причины один повтор с замечанием, затем готовый вопрос, чат остаётся у бота. Если модель ответила `answer`, а причина
есть (кроме финала), код передаёт чат сам. Вопрос цены чат не передаёт, если в заметке менеджера есть сумма. Сообщение
с номера не от бота значит, что подключился человек, и бот в этом чате выключается: для этого id своих сообщений
хранятся в `outbound_ids`.

**Определение компании** (`src/company/`, 27 файлов) самая запутанная часть. Состояния для модели: `unknown`,
`searching`, `ask_official`, `not_found`, `candidate`, `asked`, `confirmed`. Справка приходит после подтверждения:
клиент ответил «да» или сам написал название и город, и код нашёл уверенное совпадение (тогда без вопроса). Каждый
вопрос о компании задаётся один раз: название, «Вы из компании X?», официальное название. Если почта недоступна
(таймаут 3 с), бот работает без данных о компании и клиенту ничего не пишет.

**Перезапуск.** Очередь пачек только в памяти (`batcher.ts`), при штатной остановке она дорабатывается. После
аварийного падения сообщения, уже записанные в базу, сами не подхватываются: их находит только возврат чата боту
(`resume.ts`). Сообщения, пришедшие за простой, получают ответ, если им меньше 12 часов, о более старых менеджеру
уходит одно уведомление (`backlog.ts`).

**Рабочий режим.** `TEST_MODE=false` не значит «отвечать всем»: чаты, известные до переключения, остаются у менеджера,
без полного списка чатов бот не стартует (`pipeline/working-mode.ts`, `deploy/scripts/working-mode.sh`).

**Симулятор** (`tools/simulator/`): настоящая сборка бота с поддельным WhatsApp и сценариями. С `SIM_FAKE=1` бесплатен
и не выходит в сеть, показывает, что получала модель на каждом вызове (`prompts.md`). Это лучший способ увидеть
поведение без ключей.

## 8. Почта (leads)

Конвейер по кнопке (`tanbala_leads/pipeline.py`, фоновый поток): parser-2gis, затем crawl4ai, квалификация Haiku,
проверка адресов Reacher, черновик Haiku с проверками кодом и одной попыткой исправить. Статусы компании: `new`,
`crawled`, `qualified` или `rejected`, `verified`, `drafted`, `approved`, `sent`, `replied`.

- parser-2gis живёт в отдельном окружении `.venv-2gis` и вызывается как CLI: ему нужен pydantic 1, а crawl4ai 2.
- Браузеры тяжёлые, поэтому на процесс не больше 1 Chrome и 1 Chromium (`browsers.py`), проверка из WhatsApp идёт
  вперёд поиска.
- Боли компании подтверждаются дословной цитатой, код сверяет её с текстом источника.
- Бюджет `DAILY_API_BUDGET_USD=1.00` считает только расход почты и проверяется перед запуском поиска или проверки,
  идущий поиск он не останавливает. Модели в `config/models.yaml`.
- Почта принимает 20 проверок из WhatsApp в сутки (`RESEARCH_PER_DAY`), сам бот запускает не больше 10 за скользящие
  24 часа, поэтому на деле предел 10.
- Компании, которые добавила проверка из WhatsApp (`requested_via`), закрыты для рассылки триггерами базы. Владелец
  может снять отметку кнопкой, и компания снова попадёт в рассылку. Компании, уже бывшие в базе, не помечаются.
- Отправка (`steps/send.py`): адрес зашит в `TEST_RECIPIENTS`, он же в CHECK таблицы `test_sends`, `send_draft` всегда
  отказывает.
- `/internal/*` отвечает только с Host `127.0.0.1` или `localhost` и без прокси-заголовков. Токены бота и панели разные:
  токен бота не даёт одобрять письма и запускать поиск.

## 9. Безопасность и сервер

Сервер один: PS.KZ, Ubuntu 24.04, 2 vCPU, 2 ГБ памяти, swap 4 ГБ, диск 40 ГБ. База переписок намеренно лежит в
Казахстане; текст разговора при этом уходит в Claude API, голосовые в OpenRouter. Владелец собирается поднять тариф до 4 ГБ, потому что на том же сервере планируется почтовый сервер.

Слои защиты панели, снаружи внутрь:

1. Caddy: HTTPS, basic auth по строке на человека, `/internal*` отвечает 404, fail2ban на подбор.
2. Вход панели: пароль от 9 символов, ограничения на IP и имя, cookie `__Host-`, SameSite=Strict, CSRF, проверка
   Origin и Host, строгий CSP без `unsafe-inline`.
3. Три разных токена: бот↔почта, панель↔почта, панель↔бот. При совпадении службы не стартуют.
4. nftables по пользователю службы (`deploy/nftables/tanbala-guard.nft`). На 127.0.0.1 бот ходит только в 8000 и DNS,
   панель только в 8000 и 3101 и больше никуда, даже в DNS. Служба почты вместе с браузерами (правило по пользователю,
   браузеры отдельно не выделены) на 127.0.0.1 может в Postgres 5432, Reacher 8080 и порты 32768–60999; закрыты 8000,
   8001, 3100, 3101, 3200, частные сети и свой внешний IP кроме 80 и 443. Наружу бот и почта ходят свободно.
5. systemd: свой пользователь на службу, `SocketBind` на свои порты, лимиты памяти, бот умирает последним.

Модель угроз, из которой всё это выросло: бота можно атаковать сообщениями WhatsApp, браузеры почты открывают чужие
сайты без песочницы. Взлом одной службы не должен давать действий другой.

**Выкладка вручную, CI нет.** На ПК владельца `deploy/scripts/build-release.sh` собирает архив из коммита и панель,
`scp` на сервер, там `install.sh <шаги>` (`system configs caddy db leads whatsapp console`), затем `health.sh`.
Интерфейс собирается на ПК: на 2 ГБ сборка Vite мешала бы поиску.

`health.sh` идёт по таймеру раз в 5 минут и пишет только в журнал systemd: никого не оповещает. Копии баз в 03:30
лежат 7 дней в `/var/backups/tanbala` на том же сервере. Сессия WhatsApp намеренно не копируется, восстановление это
новый QR.

Замер нагрузки 02.11: CPU в среднем 2.4%, RAM в покое около 0.75 ГБ, при поиске служба почты до 1.2 ГБ, диск занят на
37%.

## 10. Как запустить на чистом клоне

Нужны Node 22.12+, Python 3.11+, для части тестов почты Docker. Ключи и `.env` не нужны. Команды ниже проверены на
чистом клоне 04.11.2026 на Windows: там вместо `.venv/bin/python` пишется `.venv/Scripts/python`, а папку клона лучше
держать с коротким путём, иначе pip падает на длинных именах.

```bash
# панель: типы, линтер, тесты с порогом покрытия 80%
cd console && npm ci && npm run check

# интерфейс панели без сервера: заглушки всех экранов на http://127.0.0.1:5173
cd console/web && npm ci && npm run dev
# крайние случаи: /?state=wa-down, /?state=leads-down, /?state=empty

# бот: типы, линтер, тесты с порогом покрытия
cd whatsapp && npm ci && npm run check

# бот без сети и без ключа: диалог, лог и всё, что получала модель
cd whatsapp && npm run build && cd tools/simulator
SIM_FAKE=1 BOT_ROOT=../.. SIM_TYPING=skip SIM_OUT=/tmp/sim-g node run.mjs scenarios/g-container-explain.json

# почта: без Postgres 1638 тестов
cd leads && python -m venv .venv && .venv/bin/python -m pip install -r requirements.lock.txt \
  && .venv/bin/python -m pip install -e . --no-deps && .venv/bin/python -m pip install 'pytest>=9,<10'
PYTHONUTF8=1 .venv/bin/python -m pytest -q -m "not db and not paid"
```

Тесты почты с маркером `db` нужен Postgres из `leads/docker-compose.yml` (переменные в `leads/.env.example`), схема
создаётся временная. Маркер `paid` не запускать: это платные вызовы.

Для живой панели на сервере владелец может завести отдельного менеджера. Паролей в этом файле нет.

## 11. Решения владельца

Это выбор бизнеса. Предлагать замену можно, но с доводами и ценой перехода.

| Решение | Почему |
| --- | --- |
| Baileys, а не официальный WhatsApp Business API | зафиксировано в плане бота; бот работает на номере Tanbala |
| Один VPS в Казахстане | база переписок лежит в стране |
| Письмо уходит только после одобрения человеком | контроль качества и репутация |
| Бот не называет цены, сроки, количество и место оборудования, модели | это делает только менеджер |
| Один голос: бот уточняет у коллеги сам, не обещает звонков | клиенту нельзя обещать за другого человека |
| Веб-интерфейс Tanbala идёт вместе с 1С, а не вместо неё | учёт всегда в 1С клиента |
| Компании, добавленные проверкой из WhatsApp, не попадают в рассылку | клиент уже пришёл сам |
| Сессия WhatsApp не копируется | она даёт полный доступ к номеру |
| Старые панели удаляются отдельным шагом | откат, пока новая панель не обкатана |

## 12. Известные слабые места

Что команда уже видит. Подтвердите, оспорьте или расставьте по важности, не описывая заново.

**Эксплуатация**

- Нет CI и нет тестового стенда: проверка только на ПК и сразу на рабочий сервер.
- Копии баз только на том же сервере: потеря VPS означает потерю всех данных.
- Нет оповещений: сбой виден только тому, кто смотрит журнал.
- Один сервер без резерва, 2 ГБ памяти, поиск уходит в swap.
- Отката нет: версий релиза на сервере нет (`install.sh` делает `rsync --delete`, `--rollback` только у сайта).
  Миграции только вперёд, бот не стартует на базе новее кода, поэтому откат кода через миграцию требует восстановления
  базы.
- Python-зависимости без хэшей, Chromium для crawl4ai не обновляется сам.

**Архитектура**

- Старые панели живут рядом с новой: код и логика двух интерфейсов в боте и почте.
- Контракты описаны текстом. Сквозных контрактных тестов нет: схемы zod панели не сверяются с настоящими ответами,
  примеры в `console/tests/helpers/fixtures.ts` написаны вручную. У почты есть только проверка списка путей и формы
  ответа боту.
- Панель опрашивает бота и почту каждые 5 с на вкладку: как это ведёт себя при нескольких менеджерах, не измерено.
- Baileys неофициальный и в версии rc: есть риск блокировки номера, поведение может измениться без предупреждения.
- Сроков хранения переписок нет: удаляются только отклонённые черновики (30 дней) и журнал панели (180 дней).
- Узкие места заложены конструкцией: один процесс бота (`process-lock.ts`), синхронный better-sqlite3 в одном потоке
  с Baileys и двумя серверами fastify; у почты один поиск и одна проверка сразу (уникальные индексы в `db.py`), а
  uvicorn, поток поиска и очередь проверок в одном процессе.
- Несколько менеджеров не продуманы: номер для уведомлений один (`MANAGER_WHATSAPP`), закрепления чатов нет. Ответ из
  панели сначала переводит чат на менеджера и только потом отправляет, поэтому при сбое отправки чат остаётся у
  менеджера. Предел панели: 20 ответов в час на чат, 100 всего.

**Бот**

- Промпты 03.11 сильно ужаты и живым Claude не проверены. Перед выкладкой нужен платный прогон симулятора.
- После аварийного падения принятые, но не отвеченные сообщения сами не подхватываются (раздел 7, «Перезапуск»).
- Проверки регулярными выражениями по русскому языку хрупкие: ложные срабатывания уже «душили» бота, а реальные сроки
  после послаблений приходилось возвращать.
- Второй отказ проверки заменяет ответ готовым вопросом, который не отвечает клиенту.
- Обычно 3 вызова Sonnet на сообщение, бывает до 5: цена и задержка не оптимизированы, варианты (кэш на час, Haiku для
  `interest` и `review`) ждут решения.
- Факты о Tanbala в двух файлах: `whatsapp/knowledge/bot.md` и `leads/knowledge/tanbala-agent.md`. Тест сверяет только
  реквизиты и дальность.

**Панель**

- У `console/web` нет ни тестов, ни ESLint. Браузерных сквозных тестов нет ни у чего.
- Нет предела запросов на сессию. Остальные хвосты в `console/docs/TODO.md`.

**Почта**

- Боевой отправки и разбора ответов нет. Письма в Gmail не доходят, пока у сервера venmart.kz нет PTR; решение идёт к
  своему почтовому серверу на `tanbala.kz`.
- Reacher на 02.11 работал с `HELO localhost` и чужим PTR, часть серверов его отвергает.

## 13. Что проверить

**Портал**

1. Верно ли разделены сервер панели и два API? Оправдан ли BFF при двух пользователях или он лишний слой?
2. Роли, сессии, CSRF: есть ли обход? Отдельно: что будет с действием при сбое на середине (ответ клиенту ушёл, журнал
   не записался; таймаут к боту).
3. Опрос каждые 5 с: нагрузка на SQLite и Postgres, кэш 1.5 с, предохранитель. Нужны ли SSE или WebSocket?
4. Схемы zod против настоящих ответов: что произойдёт, когда бот или почта поменяют поле?
5. Интерфейс: архитектура без библиотек, свой роутер, обработка ошибок, телефон.

**Архитектура в целом**

6. Три процесса, два языка, три хранилища: верные ли границы для такой команды? Что объединить или упростить?
7. Что сломается первым при 100 чатах в день и нескольких менеджерах?
8. Что обязательно сделать до `TEST_MODE=false` и до первой настоящей рассылки?
9. Надёжность бота: потеря сообщений при перезапуске, очередь, повторная отправка, разрыв связи, обработка `backlog`.
10. Данные: схемы, миграции, индексы, хранение персональных данных, восстановление из копии.

**Качество**

11. Какие части переусложнены? Определение компании, проверки кодом и 6 тысяч тестов сами по себе требуют времени на
    поддержку: где тесты закрепляют детали, а не поведение?
12. Что в коде выглядит сгенерированным и лишним: мёртвый код, лишние абстракции, дублирование?
13. Безопасность: инъекции в промпт через сообщения и сайты, SSRF браузеров почты, утечки в логах, права на сервере.
14. Выкладка: что автоматизировать в первую очередь, как откатываться.

## 14. Формат результата

Один файл `REVIEW-RESULT.md`. Если есть права на запись, ветка `review/<дата>` и pull request, иначе файл передаётся
владельцу.

```markdown
# Итог ревью

## Вывод для владельца
3–5 предложений простым языком: можно ли запускаться, что самое важное, сколько работы.

## Что сделать до запуска
Находки, которые блокируют запуск.

## Что сделать в первый месяц

## Что можно отложить

## Что сделано хорошо
Что менять не надо, чтобы это не сломали при правках.
```

Каждая находка: важность (критично, высокая, средняя, низкая), файл и строка, что не так и какой сценарий сломается,
как исправить, оценка времени. Находки без сценария отказа не нужны: важнее десять проверенных, чем сто возможных.
Владелец не читает код, поэтому вывод и заголовки находок писать так, чтобы он понял их без программиста.
