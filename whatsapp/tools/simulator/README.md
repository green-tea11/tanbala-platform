# Симулятор диалога WhatsApp-бота Tanbala

Инструмент разработки (решение владельца 01.11.2026: хранить в проекте), в сборку бота не входит, линтер его не
проверяет (`eslint.config.js`). Прогон перед выкладкой правок агента, промптов, проверок и знаний: так ошибки бота
видны до живой переписки. На сервер попадает вместе с кодом бота (`install.sh whatsapp`).

Прогоняет настоящую сборку бота (`dist/main.js`: агент, промпты, проверки кодом и проверка черновика, определение
компании через внутренний API почты, выжимка, этапы, передачи, уведомления менеджеру) с поддельным WhatsApp и
временной базой. Клиент пишет по сценарию (JSON), на выходе диалог, состояние базы после каждого хода, лог бота
и всё, что получал агент в каждом вызове Claude.

## Как устроено

- `main()` бота вызывается со швами для тестов из `MainOptions`: `startWhatsApp` (поддельное подключение),
  `createLlm`, `clock`, `logDestination`, `startPanel` и `startConsoleApi` (пустые, порт не открывается).
- Входящее идёт путём Baileys: сырое `WAMessage` → `whatsapp/message-intake.js` → `whatsapp/inbound.classifyUpsert`
  (TEST_ALLOWLIST, граница привязки, менеджер) → `main.routeEvent` (запись в базу, склейка 4 с, конвейер ответа).
- Корень проекта для бота: новая временная папка (`os.tmpdir()/tanbala-sim-XXXX`) с копией `config/models.json`
  и `knowledge/*.md` из `BOT_ROOT`. База, замок процесса, лог токенов и «папка сессии» лежат в ней.
- `.env` читается из `BOT_ROOT` тем же `loadEnvironment`, что у `cli.ts`, затем переопределения симулятора (только
  в объекте окружения этого процесса): `TEST_MODE=true`, `TEST_ALLOWLIST=<номер сценария>`, `WA_ENABLED=true` (иначе
  main не подключит конвейер; подключение поддельное), `DATABASE_PATH`, `TOKEN_LOG_PATH`, `WHATSAPP_SESSION_DIR`
  во временной папке, `MANAGER_WHATSAPP=77000000009` (поддельный, уведомления видны в транскрипте),
  `WA_CONSOLE_TOKEN` убран.
- Расшифровка голосовых: запрос к OpenRouter всегда перехватывается, ответ берётся из поля `transcript` хода (нет
  поля: отказ 503, бот шлёт фразу про голосовое). Настоящего OpenRouter нет ни в каком режиме.

Предохранители: перед стартом проверяется, что пути базы, сессии и лога токенов внутри временной папки;
`net.Server.prototype.listen` запрещён в любом режиме; в режиме подделок запрещены `fetch` наружу и любое
TCP-подключение (`net.Socket.prototype.connect`). Секреты из `.env` (имена с KEY, TOKEN, PASSWORD, SECRET)
маскируются `***` во всех файлах вывода. Строка лога «Веб-панель запущена» печатается, но порт не открывается.

## Режимы

| Режим | Как включить | Claude | Почта (leads) |
|---|---|---|---|
| Подделки | `SIM_FAKE=1` | настоящий адаптер `llm/anthropic.js` с поддельным SDK (шов `createSdk`): лимит вызовов, лог токенов, схема и разбор как в бою | поддельная (`lib/fake-leads.mjs`) |
| Без сети | `SIM_BLOCK_NET=1` | настоящий, но TCP запрещён: каждый вызов падает, бот передаёт чат (`llm_error`) | запросы падают |
| Боевой | ничего | настоящий Claude по ключу из `.env` | настоящий `EMAIL_API_URL` |

## Проверка на ПК (без сети, без Claude)

```
cd whatsapp/tools/simulator
SIM_FAKE=1 BOT_ROOT=../.. SIM_TIME_SCALE=0.25 SIM_TYPING=skip SIM_SETTLE_MS=800 SIM_OUT="$TEMP/tanbala-sim/c" node run.mjs scenarios/c-warehouse-hot.json
```

Вывод держать вне репозитория (`SIM_OUT` во временной папке): в нём переписка и промпты.

Перед этим `npm run build` в `whatsapp/` (папка `dist/` в `.gitignore`). Все сценарии так проходят за 15-25 с
каждый. `node check-secrets.mjs <BOT_ROOT> <папка вывода>` проверяет вывод на утечку значений секретов из `.env`
(печатает только число совпадений).

## Запуск на сервере

```
SIM=/opt/tanbala/whatsapp/tools/simulator
sudo setpriv --reuid=tanbala-wa --regid=tanbala-wa --init-groups -- env BOT_ROOT=/opt/tanbala/whatsapp SIM_TYPING=skip SIM_OUT=/tmp/tanbala-sim-out/a node $SIM/run.mjs $SIM/scenarios/a-kusto-logistics.json
sudo cat /tmp/tanbala-sim-out/a/transcript.md
```

`SIM_KNOWLEDGE_DIR=<папка>`: знания (`*.md`) из другой папки, чтобы проверить правку `knowledge/` до выкладки.
Около 3,5 вызова Sonnet на ответ бота, ≈ $0.1 за ответ (01.11.2026: 8 ответов ≈ $0.9, 3 ответа ≈ $0.26).
Боевой режим тратит деньги: запуск только с «ок» владельца.

`BOT_ROOT` по умолчанию `/opt/tanbala/whatsapp`. Без `SIM_OUT` вывод в `/tmp/tanbala-sim-out/<сценарий>-<время>/`
(путь печатается в конце). Файлы создаёт `tanbala-wa`, поэтому читать через `sudo`. Работающий бот не мешает:
свой замок процесса, своя база, порты не слушаются, сессия WhatsApp не трогается. Сценарии можно гонять
параллельно: у каждого запуска своя временная папка.

Расход в боевом режиме: дневной предохранитель бота (`API_DAILY_LIMIT`, `API_DAILY_LIMIT_PER_CHAT`) считается по
временной базе, то есть отдельно на каждый запуск, и счётчик настоящего бота не тратит. Сценарии a, d, f запускают
проверку новой компании в проекте B (research): это тратит бюджет Claude проекта B и его дневной лимит проверок.

## Настройки (переменные окружения)

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `BOT_ROOT` | `/opt/tanbala/whatsapp` | откуда брать `dist/`, `node_modules/`, `.env`, `config/`, `knowledge/` |
| `SIM_FAKE` | нет | `1`: подделки, сеть запрещена |
| `SIM_BLOCK_NET` | нет | `1`: боевой режим без сети (проверка сборки) |
| `SIM_OUT` | `/tmp/tanbala-sim-out/...` | папка вывода |
| `SIM_PHONE` | `phone` сценария | номер клиента (формат 77XXXXXXXXX), он же единственный в TEST_ALLOWLIST |
| `SIM_MANAGER_PHONE` | `77000000009` | номер менеджера; `none`: без номера (уведомления только в базе) |
| `SIM_TIME_SCALE` | `1` | множитель всех пауз бота (склейка, «печатает», повтор) и пауз сценария |
| `SIM_TYPING` | настоящая | `skip`: пропустить только паузу «печатает» (до 20 с на ответ) |
| `SIM_SETTLE_MS` | `2000` | сколько тишины считать концом хода бота |
| `SIM_TURN_TIMEOUT_MS` | `300000` | предел ожидания одного хода |
| `SIM_KEEP_DB` | нет | `1`: не удалять временную базу (путь печатается) |
| `SIM_FAKE_RESEARCH_MS` | `8000` | сколько идёт поддельная проверка новой компании |

## Сценарий

```json
{
  "description": "что проверяем",
  "phone": "77000000001",
  "pushName": "Тест",
  "verifiedName": "необязательно: имя бизнес-аккаунта",
  "profile": { "kind": "business", "websites": ["https://example.kz"], "email": null },
  "turns": [
    { "text": "Здравствуйте" },
    { "text": "второе сообщение подряд", "noWait": true },
    { "text": "третье через 2 с, склеится с прошлым", "waitMs": 2000 },
    { "voice": true, "seconds": 12 },
    { "voice": true, "transcript": "что сказал клиент голосом" },
    { "other": "sticker" },
    { "waitForResearchMs": 120000 },
    { "pauseMs": 5000 },
    { "comment": "пометка в транскрипте" }
  ]
}
```

- Ход с сообщением ждёт, пока бот закончит: нет вызовов Claude и запросов, нет пауз часов бота (склейка, «печатает»,
  повтор) и тихо `SIM_SETTLE_MS`. Свой предел ожидания: `timeoutMs`. `waitMs`: пауза перед отправкой (клиент думает),
  `noWait: true`: не ждать бота (следующие сообщения попадут в ту же пачку или придут во время ответа).
- `waitForResearchMs`: ждать, пока проверка новой компании в проекте B закончится (опрос статуса раз в 10 с тем же
  клиентом API, что у бота). Бот сам узнаёт итог только при следующем сообщении клиента: так устроен `pollResearch`.
- `profile`: что вернёт запрос бизнес-профиля (по умолчанию `personal`). Фото профиля нет, поэтому вызова logo нет.
- `fake`: подсказки поддельной модели, работают только при `SIM_FAKE=1`: `interest` (поля оценки: `level`,
  `companyName`, `companyCity`, `companyAliases`, `companyAnswer`, `confirmedPains`, `priceAsked`, `refused`, `profile`),
  `reply` (строка или объект `{ outcome, text, companyQuestion, stage, aboutPrice, usedFacts }`, массив: по вызовам
  хода), `review` (`{ ok, problems }` или массив). На уровне сценария `fake.companies` и `fake.researchFinds`
  дополняют справочник поддельной почты. В боевом режиме `fake` не читается.

## Что лежит в папке вывода

- `transcript.md`: шапка (режим, настройки, итог), по ходам диалог с временем по Алматы (клиент, бот клиенту
  с видом сообщения: ответ, фраза передачи, фраза про голосовое; уведомления менеджеру целиком), лента «Ход бота»
  (вызовы Claude с исходом, запросы к почте с итогом, отказы проверок, повторы, поиск и проверка компании, итог хода),
  затем состояние из базы: `chats` (status, interest_level, last_stage, told_facts, price_asks, refused_streak, bot_note),
  `chat_companies.state` целиком, `client_profiles`, все `handoffs` (открытые помечены), новые `manager_notifications`,
  `api_usage`, сообщения по автору и отметке «отвечено», отклонённые черновики хода с замечаниями.
- `log.md`: все строки pino по ходам (уровень, текст, контекст) и запросы к почте с телами запросов и ответов.
  Искать: «Черновик не прошёл проверки кодом» (коды нарушений), «Проверка не пропустила черновик», «безопасный
  вопрос», «Передача рано», «Найден кандидат», «Проверка новой компании», «Клиент отклонил/подтвердил».
- `prompts.md`: каждый вызов Claude: назначение, модель, время, блоки system по ссылке (S1, S2…), все реплики целиком
  (последняя реплика user несёт блок `<данные>`: этап, чего не хватает для расчёта, блок о компании, выжимка,
  замечания проверки), ответ после разбора адаптером. В конце тексты блоков system и JSON-схемы ответа с описаниями
  полей (их модель тоже получает).
- `summary.json`: числа по ходам (вызовы Claude по назначению, запросы к почте, тексты бота, исходы) и итог с
  токенами из лога расхода бота (`totals.tokens`: input, output, cacheRead, cacheWrite по назначению).
- `tokens.jsonl`: копия лога расхода симулятора (одна строка на вызов API). В режиме подделок токены примерные
  (знаки / 3).

Код выхода: 0 всё прошло, 3 какой-то ход не дождался бота, 1 сбой (файлы вывода всё равно пишутся).

## Сколько вызовов Claude на ход бота

По коду `pipeline/reply-flow.ts`, `pipeline/company-turn.ts`, `agent/agent.ts`:

| Ход | Вызовы |
|---|---|
| обычный ответ | 3: черновик (reply) и оценка (interest) параллельно, затем проверка (review) |
| бот ждёт ответа на «Вы из компании X?» | 3, но оценка идёт до черновика (дольше) |
| проверка или код отклонили черновик, повтор прошёл | 5 (reply, interest, review, reply, review); если первый черновик отклонил код, без первой review: 4 |
| ранний hot модели | 4 (reply hot, interest, reply, review) |
| передача кодом по цене (третий вопрос или задача понятна) | 2 (reply, interest), клиенту готовая фраза |
| финал hot с текстом модели, no_answer, asked_human | 3 |
| жалоба | 2 |
| новые сообщения пришли во время ответа | ход повторяется один раз: до ×2 |
| только голосовое без расшифровки, стикер, чат у менеджера | 0 |
| эмодзи («👍», «🙏😊») | 3, как обычный ответ |
| logo (Haiku) | не больше 1 на чат: только бизнес-аккаунт с фото профиля, если компанию не назвали (в симуляторе 0) |

Голосовое: плюс 1 вызов OpenRouter на сообщение (не Claude). Проверка новой компании тратит Claude проекта B, не бота.
Итого обычно 3 вызова на ход, в среднем около 3.3 (живой чат 7669: 20 вызовов на 6 ходов; прогоны с подделками:
2.9-3.0 на ход с ответом).

Размер одного вызова: блок знаний S1 46 656 знаков (с точкой кэша, общий для reply, interest и review), инструкция
reply 8 603, interest 5 665, review 6 340 знаков, плюс до 30 сообщений истории и блок данных (1-2 тыс. знаков).
На ход это 3 чтения кэша блока знаний (первый вызов после 5 минут тишины пишет кэш заново) и около 22 тыс. знаков
без кэша в первом ходе, 25-26 тыс. к девятому (прогоны a и c; растёт с историей). Точные токены и долю кэша даст
`summary.json` → `totals.tokens` после боевого прогона.
