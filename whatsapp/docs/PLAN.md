# WhatsApp-агент Tanbala: итоговый план

Обновлено: 29.10.2026.

## Задача

Консультант в WhatsApp на отдельном номере. Клиенты приходят с сайта и из писем, которые рассылает система `B-web-email`. Агент объясняет, как работает RFID-учёт, выясняет, что за бизнес у клиента, и передаёт горячего клиента менеджеру вместе с готовой выжимкой по разговору. Менеджеру уходит и чат, где нет ответа в знаниях, где проверка не пройдена дважды и спросить клиента уже нечего, где клиент жалуется или просит живого человека.

Агент первым делом консультант: он ведёт человека к пониманию продукта. Решение, цену и сроки даёт коллега (менеджер).

С 27.10.2026 агент определяет компанию клиента и получает от почтового проекта (проект B) то, что о ней известно: рубрику и боли. Продаёт через боли: подаёт их как то, что бывает у похожих компаний, и спрашивает. С 29.10.2026 менеджеру чат по цене уходит, только когда собран минимум для менеджера (см. «Передача менеджеру»).

## Принятые решения

- Бота пишем сами, без платных сервисов.
- Подключение к WhatsApp через Baileys. Риск бана есть и у Green API, которым мы уже пользуемся, поэтому риск принят осознанно.
- Хостинг: VPS на PS.KZ, в Казахстане. Переписки хранятся там, требование закона РК о хранении персональных данных выполняется.
- Модель: Claude через API: ответ, решение о передаче, проверка и оценка интереса на Sonnet 5.5, название с логотипа на Haiku 5.5 (решение 29.10.2026). Платим ежемесячными API-кредитами Max ($100), общими с системой писем. Обе системы тратят мало.
- Бот отвечает только на входящие сообщения. Единственное исключение: уведомления менеджеру на его номер (см. «Передача менеджеру»).
- Голосовые сообщения расшифровывает внешний API через OpenRouter: модель elevenlabs/scribe-v2 (около $0.22 за час аудио), с этапа 3.
- Вместо Telegram своя веб-панель.
- RAG пока не делаем (см. «Знания агента»).

## Компоненты

Технологии под каждый компонент выбирает агентская система. Зафиксировано только подключение к WhatsApp.

- **WhatsApp:** Baileys. Номер подключается как связанное устройство через QR-код.
- **Backend:** диалоги, статусы клиентов, логика агента.
- **Знания:** два файла в `knowledge/`, весь текст целиком в промпте с кэшированием.
- **LLM:** Claude через Anthropic API. Ответ, проверка и оценка интереса клиента (все на Sonnet) идут отдельными вызовами.
- **Голос:** внешний API распознавания речи через OpenRouter, модель в `config/models.json`.
- **Компания клиента:** внутренний API почтового проекта на `127.0.0.1` (контракт `D-Email+WhatsApp/contract/INTERNAL_API.md`): поиск компании, справка, проверка новой компании. Работает только при заданном `INTERNAL_API_TOKEN`, иначе бот ведёт себя как раньше.
- **Веб-панель:** список чатов, полная переписка, карточка клиента, ответы от имени номера.

## Знания агента

Один источник правды о Tanbala, без отдельной базы:

- `knowledge/tanbala-agent.md`: копия документа владельца, тот же файл, что в `B-web-email`. Когда документ меняется, его обновляют в обоих проектах.
- `knowledge/whatsapp.md`: правила только для WhatsApp. Если они расходятся с `tanbala-agent.md`, прав `whatsapp.md`.

Оба файла целиком идут в системный промпт и кэшируются через prompt caching. Документ небольшой, так дешевле и надёжнее RAG: раздел «Строго нельзя» всегда в промпте и не может потеряться при поиске. RAG добавим, только если база знаний вырастет в разы.

Агент не называет модели, бренды, виды меток и количество оборудования. Он говорит, что учитывать можно любые вещи, а решение подбирает коллега под задачу.

## Как обрабатывается сообщение

1. Baileys получает входящее сообщение. Если это голосовое, сначала расшифровываем его.
2. Проверяем статус чата. Если ведёт менеджер, бот молчит.
3. Сначала оценка интереса (Sonnet) обновляет выжимку по последнему сообщению клиента, затем модель ответа (Sonnet) по этой свежей выжимке пишет ответ строго по файлам знаний и решает, передавать ли чат менеджеру (01.11.2026: раньше вызовы шли параллельно, и ответ не видел, что клиент назвал в последнем сообщении; ход дольше примерно на 2.5 с при паузе «печатает» до 20 с). Если оценка не получилась, ответ пишется по прежней выжимке с пометкой, что она собрана до последнего сообщения клиента. При передаче бот сначала отвечает на вопросы, ответ на которые есть в знаниях, потом пишет «Уточню у коллеги и вернусь к вам»: всё одним сообщением, в два-три предложения. Передачу по цене без минимума для менеджера код не пропускает (см. «Передача менеджеру»). Чат сразу отмечается для менеджера, и уходит уведомление.
4. Проверки кодом, бесплатные: тире, цены и валюта, проценты, стоп-слова, ссылки, жаргон, заметки `[Проверить]`. Тот же список, что в `B-web-email`, и сверх него один голос: «специалист» и обещания за другого человека («он вам напишет») клиенту не пишутся. Цены и сроки допустимы только из заметки менеджера при возврате чата. Номера сильных сторон (F1–F10), которые модель перенесла в текст, код убирает до проверок сам, черновик из-за них не отклоняется (01.11.2026).
5. Второй вызов (Sonnet) проверяет черновик: нет ли фактов не из знаний и заметки менеджера, обещаний цен, скидок, сроков или объёмов работ. Если проверка не пройдена, бот один раз пробует заново. Второй провал не передаёт чат (решение 29.10.2026): клиенту уходит фиксированный вопрос о следующем невыясненном из квалификации, без фактов о Tanbala, не тот, что бот задал прошлым сообщением; при вопросе цены перед ним «Ориентир коллега назовёт, когда поймём ваш объект». Если клиент спрашивает цену и минимум собран, чат уходит менеджеру по цене. Нейтральная фраза «Уточню у коллеги и вернусь к вам» и передача check_failed остаются, только когда спросить нечего. Отклонённые черновики и замечания проверок видны в карточке чата в панели 30 дней. С 01.11.2026: проверка видит выжимку о клиенте и чего не хватает для расчёта и помечает каждое замечание видом: fact (факт не из документов, обещание, цена и сроки, утверждение о компании клиента, запретная тема) или style (повтор вопроса, несколько вопросов подряд, тон). Второй черновик только с замечаниями style, прошедший проверки кодом, уходит клиенту. Иначе готовый вопрос уходит с короткой реакцией перед ним: «Здравствуйте!», если бот ещё не писал; «Спасибо, это важно для расчёта.», если клиент в этом ходе назвал новое для расчёта; иначе «Спасибо!» (на ходу с вопросом цены вместо реакции фраза об ориентире). Если все готовые вопросы уже звучали, недостающее для расчёта, о котором бот спрашивал один раз, спрашивается ещё раз готовыми словами (consult.md, раздел 6). Фразы реакции ждут подтверждения владельца.
6. Ответ уходит клиенту. Обновляются карточка клиента и уровень интереса.

Перед шагом 3 бот определяет компанию клиента, сначала бесплатно: домен из бизнес-профиля WhatsApp, номер, имя профиля, название из слов клиента; только у бизнес-аккаунта логотип на фото профиля (Haiku, один раз на чат). Найденную компанию бот один раз уточняет у клиента, справку получает только после «да». Неизвестную компанию проверяет проект B (один раз на чат). API недоступен (таймаут 3 с): бот работает без данных о компании, клиенту ничего не пишет.

## Роль агента

- Объясняет, что такое RFID-учёт и что умеет Tanbala. Говорит, что решение подбирается под каждый бизнес.
- Никогда не называет цены, сроки, количество антенн и объём работ, не обещает скидок.
- На вопрос «сколько стоит» без минимума для менеджера отвечает на то, что есть в знаниях, пишет «Ориентир коллега назовёт, когда поймём ваш объект» и задаёт вопросы следующей группы. Чат не передаёт.
- Продаёт через боли из справки: подаёт их как то, что бывает у похожих компаний, и спрашивает, не утверждает. Не пересказывает, что мы о клиенте знаем, и не ссылается на его сайт или 2ГИС. Общий принцип работы (ридеры с антеннами на входах и выходах, а не на каждой полке) объясняет любому клиенту, решение под объект не предлагает.
- Что выяснить: тип бизнеса, площадь, что учитывать (только ввоз и вывоз или где лежит каждая вещь), примерное число вещей, есть ли 1С, какую проблему клиент хочет решить.
- Вопросы задаёт группами, без анкеты: в сообщении не больше одного блока из двух или трёх связанных вопросов (решение владельца 29.10.2026 вечером).
- Пока чат ни разу не передавался, он уходит коллеге (hot) сам: как только собран минимум, даже без вопроса цены («Спасибо, этого хватит, чтобы коллега назвал ориентир. Уточню у коллеги и вернусь к вам.»), или на пятом сообщении клиента без минимума («Спасибо! Уточню у коллеги и вернусь к вам.»). Это держит код (`pipeline/auto-handoff.ts`). Фраза об ориентире только в ответ на вопрос цены (проверка кодом).

## Стиль и кто пишет

- Пишет как толковый живой менеджер: коротко, одна полезная фраза и блок вопросов. Без тире, списков, жирного шрифта, эмодзи, шаблонных фраз и вступлений вроде «Понятно, у вас…», не повторяет уже данные объяснения.
- Сам никогда не сообщает, что он бот, и ведёт разговор как сотрудник Tanbala.
- Если клиент прямо спрашивает, бот ли это, отвечает честно: это автоматический помощник Tanbala, и при желании подключится коллега.
- Говорит одним голосом и не обещает время ответа: не «сейчас подключится» и не «специалист вам напишет», а «Уточню у коллеги и вернусь к вам».

## Передача менеджеру

Уровни интереса:

- **Холодный:** спрашивает в общем, что это такое.
- **Тёплый:** рассказывает о своём бизнесе и задаче.
- **Горячий:** клиент согласился, что трудность у него есть, или рассказал о задаче, и спрашивает цену, сроки или договор; или спрашивает цену четвёртый раз; или отказывается отвечать и спрашивает цену; или просит живого человека. При передаче после вопроса цены бот пишет: «Цена сильно зависит от объёма. Уточню у коллеги и вернусь к вам.»

Что бот выясняет, группами по порядку (решение владельца 29.10.2026 вечером), в сообщении один блок из двух или трёх связанных вопросов и не больше одной полезной фразы (трудности похожих бизнесов, как работает учёт): 1) компанию и чем она занимается; 2) что учитывать (какие вещи, в чём: коробки, паллеты, поштучно; материал: металл и жидкости важны для меток); 3) где и сколько (город, тип помещения, примерное число вещей); 4) 1С и какая конфигурация. Площадь, движение вещей, нынешний учёт и что мешает только в довесок к группе. Минимум перед передачей по цене (решение владельца 29.10.2026, второй круг): название компании (подтверждённое через API или со слов клиента; если о компании спросить уже нельзя, она не мешает), какие вещи и материал, примерное число вещей, город и тип помещения, есть ли 1С. Клиент спросил цену, а минимума нет: бот отвечает из знаний, пишет «Ориентир коллега назовёт, когда поймём ваш объект» и задаёт вопросы следующей группы. Это правило проверяет код: ранний hot по цене получает один повтор с замечанием, а если модель снова хочет передать чат, клиенту уходит фиксированный вопрос о первой группе недостающего. Без минимума чат передаётся сразу, только если клиент просит живого человека, отказывается отвечать, спрашивает цену четвёртый раз или жалуется; отказ отвечать и четвёртый вопрос цены передают чат кодом. Сейчас код считает вопросы цены с последнего возврата чата боту: это решение реализации, оно ждёт подтверждения владельца.

Когда чат нужно передать (клиент горячий, ответа нет в знаниях, проверка не пройдена, клиент жалуется или просит живого человека):

- бот пишет клиенту «Уточню у коллеги и вернусь к вам» (при жалобе с извинением), без указания времени;
- бот отправляет уведомление на номер менеджера (`MANAGER_WHATSAPP` в `.env`): имя и номер клиента, уровень интереса, выжимка (компания и чем занимается, вещи, в чём лежат, материал, город, помещение, площадь, число вещей и как часто движутся, что отмечать, учёт сейчас, что мешает, 1С и какая, особенности); выводы из слов клиента идут с пометкой «вероятно», например «1С: вероятно есть, конфигурация не выяснена», и для минимума считаются выясненными, пока клиент не скажет иначе, что из минимума для цены собрано и что выяснить не удалось, причина передачи, компания (или «не определена») со ссылкой на карточку в интерфейсе проекта B (`EMAIL_UI_URL`) и боли, которые клиент подтвердил;
- в веб-панели чат отмечается для менеджера с той же выжимкой;
- бот в этом чате замолкает;
- если сообщение в чат отправлено не ботом (с телефона или из панели), это значит, что подключился человек, и бот выключается в этом чате;
- вернуть чат боту можно вручную из панели. После возврата бот отвечает на сообщения клиента, пришедшие после последнего исходящего (бота или менеджера) и не старше 12 часов (`BACKLOG_MAX_AGE_HOURS`), одним ответом; если менеджер на них уже ответил, бот молчит. Сверх этого (решение реализации, ждёт подтверждения владельца): если при возврате есть заметка, клиент молчал после фразы передачи бота и человек после неё не писал, бот возвращается к сообщениям, на которые ответила фраза передачи (не старше 12 часов), и отвечает по заметке; без заметки молчит;
- при возврате менеджер может оставить заметку для бота (до 1000 символов, клиент её не видит). Она хранится в чате до следующей передачи и идёт в промпт ответа и проверки отдельным доверенным блоком «Указание коллеги». Задание («узнай количество и 1С») бот выясняет группами вопросов, ответ клиенту («ориентир от X, нужен выезд») передаёт своими словами как ответ коллеги; цифры и обещания только из заметки, без неё бот цену не называет никогда.

## Технические правила

- **Свои сообщения:** Baileys видит все сообщения от номера, включая ответы бота. ID каждого сообщения, отправленного ботом, сохраняется в базе. Сообщение «от номера» с неизвестным ID означает, что пишет человек.
- **Сессия WhatsApp:** папка авторизации Baileys даёт полный доступ к номеру. Она в `.gitignore` и никуда не копируется.
- **Ключи:** ключ Claude API в переменной `VENMART_ANTHROPIC_KEY`, передаётся в SDK явно. Переменную `ANTHROPIC_API_KEY` не использовать нигде. Для этого проекта отдельный ключ в той же организации Console.
- **Модели:** в `config`, меняются без правки кода. Ответ, решение о передаче, проверка и оценка интереса на Sonnet, логотип на Haiku.
- **Расход:** каждый вызов API пишется в лог: модель, входные и выходные токены.
- **Веб-панель:** пароль из `.env` (`ADMIN_PASSWORD`, по умолчанию `admin`). Пока проект на ПК, панель слушает только `127.0.0.1`. Если пароль `admin`, панель отказывается запускаться на любом другом адресе. На VPS только HTTPS и сложный пароль.

## Порядок работ

1. Структура проекта, зависимости, `.env.example`, файлы знаний, заготовки модулей.
2. Подключить Baileys и принимать сообщения на рабочем номере в закрытом режиме: только номера из `TEST_ALLOWLIST`.
3. Backend: ответ через Haiku по файлам знаний и расшифровка голосовых (перенесена с этапа 7).
4. Проверки кодом, проверка вторым вызовом, оценка уровня интереса.
5. Передача менеджеру: уведомление на его номер и отметка в базе.
6. Веб-панель.
7. Расшифровка голосовых: перенесена в этап 3.
8. Тест на своих номерах, потом запуск на VPS и реальных клиентах.
9. Определение компании клиента и продажа через боли (27.10.2026): на моках по контракту проекта B. Живую связь с проектом B делает отдельный агент в `D-Email+WhatsApp`.
